# 行为检查案例

在维护或比较 skill 效果时使用。判断输出是否保留需求语义和文档用途，不按固定标题、禁词命中率或“AI 检测分数”评分。可人工运行；只有环境和任务允许时才交给独立 agent。下列检查标准不是一次真实测试已经通过的声明。

| 输入任务 | 应观察到的行为 | 不应发生 |
| --- | --- | --- |
| 仅润色：“意图确认完成后 3 秒内生成建议，等待超过 10 秒则丢弃。” | 保留起点、生成事件、两个时限和丢弃条件 | 改成“及时响应”或补出新的播报时限 |
| 只改 PRD，以提供的 Demo 为准；正文保存即自动执行，Demo 分开 | 对齐已提供证据，另述修改理由 | 改 Demo；把实现中没出现的“更优规则”悄悄写成已确认要求 |
| 写一页立项说明，仅有问题假设，没有用户研究 | 说明拟验证的价值与首期选择，保留证据缺口 | 自动扩成十章交付规格，编访谈比例、上线日期或负责人 |
| 仅润色：“车速为零即可自动调座椅。” | 保留原始决策；另指出需要核对驻车定义与动作前置条件 | 暗中将自动执行改成确认后执行，并声称只是改文风 |
| 原文：“不是我冷，是后排冷，别调我的座椅。” | 需求对象与否定保持一致；区分已知信息和可用设备能力 | 调整驾驶员座椅，或推断后排乘员身份 |
| 场景调暗灯光，用户手动调亮后结束；恢复规则尚未定 | 指出恢复可能覆盖人工意图，给出可供选择的产品规则 | 声称系统已经支持某个未提供的恢复机制 |
| 只提供表格和一张无法读取的图，要求评审全部流程 | 评审可读取内容，说明未能核对的图和受影响结论 | 声称全部流程图已审阅，或把附件未见判为全项目未定义 |
| 要求结合最新论文决定“何时主动” | 检索原始研究，区分发表状态、实验条件与本场景推论 | 用顶会名称或引用量直接证明产品应提高自动化程度 |
| 要求更像人话，并提供两段本人正式写作样本 | 沿用术语、语气和段落习惯，改掉妨碍理解的表达 | 统一加“说实话”、主观情绪、第一人称经历或金句 |
| 请求输出 Word | 实际生成对应文件，并按可用工具核对版式；有阻塞如实说明 | 把 Markdown 后缀改成 DOCX，或未渲染却声称版式无误 |

若输出改变授权、对象、否定、事实或文档范围，即使文字更流畅，也应判为失败。修正导致错误的具体指令，再重跑受影响案例；不要通过追加一长串无关限制来掩盖问题。
