# 结构与座舱检查

## 选结构，不填空表

保留团队已经采用且可读的模板。没有模板时，可按“问题与目标 → 本期方案 → 关键场景和规则 → 验证与依赖”组织，章节名称和数量随内容调整。小功能可以是一两页，复杂编排可以用附录承载明细；不要按篇幅证明完整性。

开头的一两段应使读者知道这次要解决什么、方案改变了什么、当前需要评审什么。文档阶段、版本和责任人有资料就记录；缺失时不要编姓名或日期。

### 问题与目标

讲清具体对象和处境，再解释现在的困难。区分用户明确提出的问题与产品团队的机会假设。战略投入可以有自己的理由，但不能代替具体场景的需求证据。

一个足够好的论证顺序是：现有方式产生了什么负担，方案减少哪一步判断或操作，为什么这种帮助适合当前时机，现阶段靠什么验证。没有现状数据时保留定性描述，不补造发生频次。

### 本期方案

说明用户能够获得哪些帮助，哪些能力已可复用，哪些依赖需要验证。界定范围时解释真实取舍，避免自动加入与本需求无关的“不做清单”。

例如，需要确认的多设备建议与持续自动执行规则涉及不同授权，应分别写清；不能只写一个“用户采纳”的入口把它们合并。

### 关键场景和规则

优先写一个读者能完整走通的场景，再提炼共用规则。相似场景可以用条件差异表说明，避免每个场景重复一整套背景和术语。

行为描述要能找到适用条件、触发、系统反应、用户操作和结果。只补会改变结果的异常，不为立项稿穷举设备错误码。交付阶段再补足影响实现和验证的细节。

### 验证与依赖

需求验收用可观察的行为描述；用户价值用实际任务结果、体验反馈或合理实验验证。二者不要相互替代。

指标写清事件、分子分母和观察时段。只在资料支持时给目标；若目标尚需决策，说明准备怎样确定。所需能力、当前状态、影响范围和负责团队放在一起，避免“能力已齐”与依赖未定并存。

## 座舱场景中会改变行为的条件

以下是检查视角，按功能选用，不能全部变成强制章节或无来源的整车规则。

| 维度 | 需要弄清的问题 | 容易写错的地方 |
| --- | --- | --- |
| 车辆与使用状态 | 驻车、临时停车、行驶是否影响可用动作和交互？依据哪个项目状态定义？ | 用车速为零替代驻车，或把用户确认当作所有动作的放行条件 |
| 人与对象 | 谁说的、谁有控制权、影响哪个座位或设备？ | 把在座信号当身份，把“后排有人”写成“有儿童”，把语音对象默认为驾驶员 |
| 触发与时机 | 显式指令、向助手表达处境、被动观察分别允许触发什么？等待期间是否过期？ | 听到处境词就出方案；导航、来电或新指令后仍播报旧建议 |
| 当前状态与动作 | 动作针对什么问题，设备是否已处于目标状态，是否具备实际控制能力？ | 为组合而凑动作，给不存在或已满足的能力作承诺 |
| 交互与授权 | 告知哪些关键变化，确认针对哪版方案，是本次应用还是长期规则？ | 一句“好”授权未告知动作，保存时顺带开启自动执行 |
| 执行与接管 | 如何处理状态变化、部分成功、延时动作、人工接管及结束恢复？ | 接口受理等于设备完成；撤销覆盖了用户后续手动调整 |
| 偏好与数据 | 哪些信息已授权使用，临时反馈是否进入长期偏好，如何纠正？ | “这次不用”直接变成长期厌恶；座舱对话自动成为学习材料 |

动作限制需来自车型能力表和项目的整车约束。未知时写明待确认的具体条件，不能把通用写作建议包装成法规或量产安全结论。

## 写主动智能方案时

先判断是否有依据发现车辆能够改善的问题，再判断帮助的收益是否足以抵消误判和打扰。正常回应、简短澄清、提出建议和直接执行是不同选择；是否执行还取决于授权和实时前置条件。

“天气不好”“路还很长”本身不能推出空调、音乐或按摩需求。明确处境可以支撑某些动作，偏好和当前状态会进一步改变方案。每个动作都应有自己的理由，不设置“必须两个以上动作”来证明主动价值。

交付稿应区分至少这些语义，只写本产品实际支持的操作：本次应用、保存方案、启用自动触发、本次不用、以后少提或不再提、撤销本次、删除偏好。命名可以沿用产品，但不能暗中扩大含义。

观察学习、打扰额度和自动执行权限分别由什么决定，需要能说清。不要把“语音变卡片”直接解释成更高信任，也不要把忽略和删除直接解释为长期负反馈。

## 检查流程图

先看实际图形，登记它描述的是判断、交互还是状态；不把三者强行塞进同一条升级轴。逐条检查：

- 分支条件能否由真实输入判断；有无缺失、冲突或把推断写成事实的条件。
- 等待、取消、失败和结束是否有去向；只检查该图责任范围内的分支，跨图连接应明确。
- 建议生成与执行授权有无分开；确认后方案变化是否需要重新确认。
- 文本、图、按钮文案及基准 Demo 是否描述同一种行为。存在差异时按用户指定的依据修订，并说明涉及的图。

复杂流程可拆成判断流程、交互流程与执行状态图，但只有拆开后更容易理解才拆。图中的判断词应具体；“智能决策”“策略仲裁”不能充当缺失的产品规则。

## 研究如何进入文档

仅在问题需要外部证据或用户要求调研时研究。优先读论文原文、作者资料和厂商官方说明，核对发表时间、场景、研究对象及结论范围。预印本与正式发表、实证结果与设计主张分开描述。

将研究落到一个具体判断：它支持哪种交互、适用条件是什么、在本项目还需要验证什么。顶会、引用量和演示成功都不能单独证明座舱场景成立。最新性需要当次检索，高引用需要有日期的可核验数据；不要在 skill 中长期保存会过期的“最新排名”。
