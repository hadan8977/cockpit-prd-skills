# 座舱 PRD 写作

让评审者读懂产品经理的判断，让设计和研发能够据此讨论行为。语言自然，取决于具体问题、充分理由和准确规则；删掉几个高频词不能替代这些工作。

## 先确定这次要交付什么

从用户给出的材料和对话判断用途，沿用已回答的信息。缺少关键产品决策时，先完成不受影响的部分，再提出具体问题；常规写作选择自行处理。

- **立项或探索方案**：重点解释问题为什么值得解决、准备验证什么，以及首期选择。不要扩写成量产交付规格。
- **方案评审或研发交付**：按成熟度补足状态、动作、交互、异常与验收；读 [结构与座舱检查](references/structure-and-cockpit.md)。
- **严格评审**：指出原文位置、问题产生的具体后果、建议改法。区别正文矛盾、附件未提供和单纯写作偏好，不把缺少材料说成项目没有能力。
- **仅润色或轻改**：保留范围、数字、否定、责任主体及确定程度。发现逻辑错误可以另行指出，不能以润色名义修改产品决策。

有用户模板或认可的写作样本时优先沿用。没有时采用简洁、平实的中文产品文档语气；不要求用户先填一套问卷。

## 确认依据与修改权限

先读实际材料，包括与需求有关的表格、流程图和原型状态。无法查看的部分如实说明。图片里的规则不能仅凭附近正文推测。

按用户本次指定的优先级处理材料冲突。用户明确“以 Demo 为准”时，记录所核对的版本，并让文档与之对齐；未指定时，不能仅因代码已存在就把实现当成已批准的需求。现有实现、已确认要求和拟议改进要能区分。

文档任务不会自动授权修改 Demo、重建产品或发布到外部。评审意见进入正式需求时，应有本次修订授权；仍需选择的重大方案写为建议或待决事项。

引用访谈、体验、数据和竞品结论时保留来源。没有证据的收益写为预期，设计阈值写为待验证假设。未测量不写“已验证”，没有统计口径不写“显著提升”。

## 先把产品判断写成立

围绕主要场景展开：用户在什么处境下，当前怎样处理，哪里费力或容易出错，方案准备怎样改善，以及为什么选择这种处理方式。只写与本需求有关的背景，避免从“智能化浪潮”开篇。

一项建议动作应能找到它所服务的问题。动作多、自动化程度高、使用大模型，都不能单独证明用户价值。有关键取舍时给出理由，例如为什么本期要求确认、为什么某类情况暂不建议；不为每项小功能强行罗列备选方案。

把能力与行为分开写。“能够识别意图”不足以指导交互，需要说明识别后何时回应、呈现什么、谁确认、改变哪些对象，以及何时退出。内部模块名只在它影响用户行为或跨团队责任时进入正文。

按文档阶段选择必要的验收证据。执行成功、用户觉得有用、愿意保存、愿意长期自动执行是不同问题，不合并成一个“采纳率”。未经提供的目标值、时限和责任人不得补造成事实。

## 再把话写顺

首次完整写作或大幅润色时，读 [中文改写示例](references/chinese-examples.md)。短句轻改可直接使用以下原则。

- 段落先讲本段要表达的事实或判断，后面的句子说明原因、行为或限制。重要处展开，简单事实一句说清。
- 多写具体主语、动作和对象。把“构建低打扰闭环”展开成真正采用的交互规则；如果规则还没定，就承认没定，不能编一个具体例子冒充需求。
- 正文用连贯段落承载解释，表格用于比较、映射和重复结构，列表用于步骤或并列要求。避免一两句话一个小标题、每句加粗标签、所有段落都凑成三点。
- 保留必要术语和稳定名词。“保存场景”不要为了避免重复而轮换成“沉淀偏好”“固化策略”。应、可、仅、不、默认、至少等词涉及规则强度，不能随意删改。
- 自然不等于闲聊。不要加入“说实话”、段子、虚构经历、故意不规整的表达，或没有来源的个人感受。允许正常连接词和正式句式，不用禁词数量判断质量。
- 不在文档正文保留“以下为你整理”“我们可以进一步”等对话句，也不反复总结已说过的意义。

若已安装 `humanizer-zh`，可在产品规则确定后使用它做语言复核；本 skill 已包含必要写作原则，不依赖该 skill 才能工作。润色后逐项核对原有数字、条件、对象、否定和授权范围。

## 交付前检查

从实际材料选一个主要场景和一个会改变结果的边界情况，沿正文和图走一遍。检查读者能否回答：为什么此时需要这个功能，接下来发生什么，用户能怎样干预，什么算结束。不要为了符合检查项给无关功能增加流程。

发现无依据的承诺、互相矛盾的行为或遗漏的重大决策时，修订已授权的内容，保留确需决策的问题。不要用更流畅的语言掩盖它们。

交付形式跟随请求：

- 新写 PRD：给可直接使用的正文；未决问题仅保留会影响范围、体验或交付的事项。
- 修订 PRD：给干净正文，并另附简短修改说明，说明实质变化及其理由。只润色时通常一句说明即可。
- 评审：按问题影响组织意见，不给缺乏依据的精确评分，不把全部意见写成同一严重等级。
- Word 文件：使用当前环境实际可用的文档生成能力；若有专门的文档 skill，读取并遵循其排版与渲染检查要求。确认表格、图、分页、图注和引用可读后再称为已检查的 Word 文档；Markdown 不能冒充 DOCX。

本 skill 与 `prd-to-prototype` 分工：这里负责需求文档，后者在用户要求构建原型时承接。不要因两者都可用就自动开始编码。
